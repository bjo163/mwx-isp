# MWX-ISP Feature Checklist

Development roadmap: [docs/roadmap.md](roadmap.md)

## Audit follow-up (2026-10-05)

The October 2026 static audit at local baseline `8de4dc5` recorded 20 implementation findings/gaps, 15 verification/hardening tasks and 10 unscheduled proposals. Its A/H follow-ups are closed in M18; the F proposals remain unscheduled. These were static-review findings, so previously delivered feature labels do not certify subsequently added surfaces.

M18 maps containment and verification to existing API, UI, storage, billing, deployment and tenant boundaries. Existing public payment mutations, public tenant scoping, voucher consistency and application JSON backup coverage require follow-up. Repairing existing unsafe behavior does not authorize extending a payment, captive-portal or CRM product.

Scope drift is reconciled by A20 in [Existing Surface Scope Inventory](#existing-surface-scope-inventory-a20-2026-10-27): portal, vouchers, tickets, IPAM and ODP already exist in code, so each is mapped to a keep/harden/hide decision. Those decisions are containment rules, not approval for expansion. The non-goals below remain in force; no inventory row authorizes a new product capability, and any expansion still needs an approved feature ID. F03/F04/F05/F10 remain proposals requiring scope review; all F items remain unscheduled. English/Indonesian handbook claims must follow the resulting implementation and evidence.

This document is the feature scope baseline for MWX-ISP. Future requirements, issues, pull requests, and code changes must first align with the feature IDs in this checklist. If a request cannot be mapped to an existing feature ID, update this checklist with the scope change before implementation starts.

## Maintenance Rules

1. Every new requirement must reference at least one feature ID, such as `TR-F001`.
2. When adding, splitting, retiring, or changing the direction of a feature, update this checklist first with the status, scope, and acceptance boundary.
3. Features should be delivered in MVP-sized increments: each change must be verifiable, rollback-safe, independently usable, and scoped to the smallest useful unit.
4. Product directions outside this checklist are not default development directions. Add them to the checklist first when there is clear agreement to proceed.
5. This checklist describes product capability boundaries. Concrete APIs, structs, and algorithms remain documented by code, tests, and inline comments.

## Status Definitions

| Status | Meaning |
| --- | --- |
| Core baseline | Mainline project capability. Future changes must preserve compatibility and stability first. |
| Implemented | The main implementation loop exists in code and can continue to receive tests, UX improvements, or edge-case hardening. |
| Partially implemented | Code has an entry point or prototype, but it must not be treated as complete production capability by default. |
| Extensible | This is an allowed extension direction, but it must follow existing architecture and test boundaries. |
| Non-goal | This is not a default project direction at this stage. |
| Planned | Scope is approved and defined, but implementation is not yet complete. |
